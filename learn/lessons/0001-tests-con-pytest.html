Lección 1: Tests con pytest

Comprobar tu código con código, sin abrir Ableton.

Qué es un test

Un test es código que llama a tu código y comprueba el resultado.

Hoy compruebas send() a mano: corres scratch.py, miras que salga 123.0. Un test es exactamente eso, pero escrito una vez y corrido mil veces, sin mirar tú.

Por qué

  • Corre sin Ableton abierto.
  • Dentro de dos meses cambias parse() y el test te avisa en un segundo si rompiste algo.
  • El test documenta cómo se usa la función.

assert

assert es la pieza central. assert <expresión>: si es verdadera no pasa nada; si es falsa, para con AssertionError.

Escríbelo tú en la consola de Python:

>>> assert 2 + 2 == 4
>>> assert 2 + 2 == 5
Traceback (most recent call last):
  ...
AssertionError

La primera no dice nada. La segunda peta. Eso es todo lo que hace.

Las tres reglas de pytest

pytest encuentra tus tests solo si:

  1. El fichero está en tests/ y se llama test_algo.py.
  2. La función se llama test_algo.
  3. Dentro hay assert.

Nada más.

Anatomía de un test

Un ejemplo de usar y tirar, fuera del proyecto.

doble.py

def doble(x):
    return x * 2

test_doble.py

from doble import doble


def test_doble_de_tres():
    resultado = doble(3)
    assert resultado == 6

Todo test sigue el mismo patrón:

  • Preparar: los datos de entrada. Aquí, el 3.
  • Ejecutar: llamar a la función. resultado = doble(3).
  • Comprobar: el assert. assert resultado == 6.

Guarda lo que devuelve la función en una variable. Luego comparas esa variable. Nunca compares la entrada.

Correrlo y leer la salida

Desde la carpeta del proyecto:

.venv\Scripts\python -m pytest

Si pasa, la salida acaba así:

tests\test_doble.py .                                    [100%]

============================ 1 passed in 0.02s ============================

Ahora cambia el assert a == 7 y vuelve a correrlo. pytest te enseña esto:

    def test_doble_de_tres():
        resultado = doble(3)
>       assert resultado == 7
E       assert 6 == 7
  • La línea con > es dónde falló.
  • La línea con E es lo que pytest encontró (6) frente a lo que esperabas (7).

Lee siempre la línea E primero.

Un test que no puede fallar es inútil

def test_malo():
    resultado = doble(3)
    if resultado == 6:
        return

Si doble devolviera 99, este test pasa igual. No hay assert, no hay test. Regla: todo test tiene que poder ponerse rojo.

Comprueba

1. ¿Qué hace assert x == 3 cuando x vale 5?

5 == 3 es falso, así que assert para con AssertionError. Nunca imprime nada por su cuenta.

2. pytest ignora una función de test si...

pytest busca por nombre. Una función comprobar_doble no la corre nunca, aunque esté llena de assert.

3. En la salida de pytest, la línea que empieza por E te dice...

En E assert 6 == 7, el 6 es lo que devolvió tu función de verdad. Ahí empieza el diagnóstico.

Ahora en Re-track

retrack/live.py tiene parse(texto): recibe un string JSON y devuelve un dict (o peta si hay error). El fichero tests/test_live.py ya existe con un intento roto.

  1. Deja el fichero así de vacío: solo from retrack.live import parse arriba.
  2. Escribe test_parse_success.
    • Preparar: texto = '{"status": "success", "result": {"tempo": 123.0}}'
    • Ejecutar: guarda lo que devuelve parse(texto) en una variable.
    • Comprobar: un assert que compare el tempo que hay dentro de esa variable con 123.0.
  3. Corre .venv\Scripts\python -m pytest. Objetivo: 1 passed.
  4. Comprueba que el test puede fallar: cambia 123.0 por 999 en el assert, corre, mira la línea E, vuelve a dejar 123.0.
